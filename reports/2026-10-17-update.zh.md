# dsh-jev-mode：2026-10-17 检查与优化更新报告

> 发布补记：本文保留审查时的候选状态。0.4.3 发布前已补齐取消/排队与后端故障隔离、凭据期限、授权快照及下游等待后的失效检查，并加入原生宿主回归。最终状态以 [CHANGELOG](../CHANGELOG.md) 和 [VALIDATION](../VALIDATION.md) 为准；新功能与模型实验仍未启用。

对象：已发布的 0.4.2；本地修复候选：0.4.3。审查基线为公开仓库提交 `8184d84`。资料检索截至 2026-10-17，时间采用北京时间。本文将已修复问题、仍存在的限制和拟议实验分开记录；社区项目的数字不视为本插件的成绩。

## 结论与建议顺序

现在最有价值的一次更新是：先交付原生尺寸 UI 和四项可复现的可靠性修复，再补齐风险分类覆盖与观测数据。下一项功能实验优先选择**保留完整目录的技能选择提示**，先以不改变行为的影子模式评估，不再扩展机械“选文件”，也不直接替换整个 Agent Loop。

本次没有重新跑计费主模型/JEV 的任务 A/B，没有校准危险授权阈值，也没有证明生产误放行率下降或总体 P95 改善。明确读取的旧收益仍主要来自代码前置读取，不能归因于 JEV。

### 必须正视：分类器漏检

以下仅调用 classifyAction，未执行命令，0.4.2 和本次候选均将它们分为 risk=1，低于默认 gateAtRisk=2：

```text
npm --prefix subproject publish
git -C subproject push
gh api --method POST repos/example/repo/releases
python deploy.py
```

前三个例子表明参数位置或通用 API 入口能绕开现有的直接动词正则；第四个说明脚本的副作用无法仅凭命令名称得知。不能因此声称“所有高危险命令都已被 JEV 检查”。本次保留标准 Shell 路径，未用“一律调用 JEV”制造新的普通任务开销。下一步应优先采用宿主可用的结构化执行/权限检查结果，保留路径围栏与人工审批；只对支持的命令语法做确定性解析，未知行为不自动取得额外权限。继续堆正则只能局部增加覆盖。

### 需要独立验证的性能问题

1. 台账写入处于调用关键路径。慢磁盘/大队列可能增加尾延迟，但没有证据证明它就是旧报告 P95 的全部原因。建议改成有界异步队列，计数同步、落盘异步、退出 flush；丢弃只影响观测数据，绝不能改变授权结果。用注入 20/100ms I/O 延迟的对照证明模型/工具是否仍被等待。
2. 排队时间、网络时间、重试等待和台账时间目前没有拆开。`pipeline.stats.calls` 更接近决策尝试次数，并不等于真实网络请求数；重试还可能令两者分离。应分别记录 admitted/queued/cancelled/providerRequests/retries，与主模型请求和 cache hit/miss tokens 分开。
3. 决策 `available()` 在 timeout 之前等待。下一版将期限覆盖凭据解析、排队、请求和解析全链，并避免把用户主动取消计成后端故障。
4. Shell 分类仍需完整文本，而授权 state 的动作描述限制为 2000 字符；不能在截断后自动肯定一个未完整呈现的高风险动作。应发送结构化目标、动作摘要及完整参数哈希，并在不完整时返回人工审批。

## 这两周及当前生态，有哪些值得采用的进展

下面区分实际新增提交与“目前值得借鉴、未证明最近才出现”的技术。

### 官方 Harness：兼容性已经在移动

官方 2026-10-16 发布了 [0.2.1-alpha.5](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.5)。我们的真实运行回归仍以 0.2.0-rc.2 为准；本次读取了官方最新 ModelsSection CSS，其行尺寸规范与修复采用的基准一致。源码相符不等于完成新宿主运行验收。

建议把 0.2.0-rc.2 与选定的 0.2.1 版本纳入独立宿主矩阵，覆盖 preset 组合、credentials、槽位、pre-step/tool waterfall、V4 持久化和最小安装。不要通过 copying 新标准预设就宣布兼容。官方 [Auto review](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/auto-review/README.md) 自身也是实验功能，不能把其名字当成安全保证。

### 最值得先试：保留目录的技能选择提示

TypeSafe 官方 [Skill suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion) 给出了分阶段排名和复核：保留完整 skill roster，只告知相关条目，可拒绝全部候选。它报告在自己的 Hermes/Haiku、488 条单轮请求上，错误加载从 16.8% 降至 7.3%，无匹配仍加载从 9.8% 降至 4.0%。请求包含生成样本、标签和任务难度有局限，不能迁移为本插件准确率。这个方法不是“最近两周才发明”的断言。

对本插件的具体适配建议：

1. 第一版只在技能较多、名称确有歧义且用户未明确指定技能的回合触发。明确命中、无适用技能、普通回复继续零 JEV。
2. 输入为本回合请求和技能元数据；不发送任意工作区文件全文。代码建立候选集，模型只返回已知 id 或 none，不生成工具参数。
3. 保留原工具目录及技能索引。建议经现有 producer-owned 通知追加到新历史，不回写 retained system prefix；主模型可以忽略建议。
4. 首轮默认 shadow：只记“若启用将提示什么”，不影响行为。确认样本正确率和端到端收益后再允许用户开启。

这是比“动态删去大部分工具”更适合本项目约束的方向，但官方方案需要两次 TypeSafe 请求，可能只改善选择而不提速。建议把“错误技能导致的多轮读取、重复执行”作为收益来源，并明确计入两次请求成本。若普通任务变慢或未减少错误选择，应保持关闭。相关 [社区多功能插件](https://github.com/luobosibing2/dsh-jev-plugin) 在 10 月仍活跃，提供独立开关、记录和恢复入口；可借鉴这些产品边界，不照搬其全部功能。

### 安全方向：一个请求内拆开原子判断，而非一个模糊大分数

官方 [System One 说明](https://docs.typesafe.ai/introduction) 支持同一状态的多问题独立并行。[OpenRouter 的授权示例](https://openrouter.ai/docs/cookbook/building-agents/gate-tool-calls-with-jev) 与 [dsh-jev-interceptor 的接入点清单](https://github.com/AskTheWay/dsh-jev-interceptor/blob/main/docs/jev-usage-points.md) 提供可参考的实现边界。

建议在已被硬规则选中的灰度动作上，一次请求分别询问 scope_match、explicit_authorization、authorization_revoked、action_context_complete、injection_suspected，结果在代码中合成。完整性不足、撤回或冲突时进入人工审批；任何 JEV 输出都不得覆盖硬拒绝/宿主权限。多问题不意味着结果独立正确，不能把各概率简单相乘后称为安全保证，也不能为了少一个人工弹窗扩大权限。

### 校准与 abstain：先有本领域标签，再谈保证

官方 [Confidence](https://docs.typesafe.ai/confidence) 明确 Choice confidence 是分布统计量，不是“系统判断正确率”；Noul 没有单独 confidence。当前 dispatch 的四个选项、confidence≥0.9 相当于 top probability 至少约 0.925，和另一个 probability≥0.9 条件并非两个独立证据。这值得记录，但不构成降阈值理由。

[jev-certify](https://github.com/nikkoxgonzales/jev-certify) 展示 conformal risk control 与分布偏移时保证失效；[独立校准审计](https://github.com/tapesymbolstate/jev-calibration-audit) 则研究无答案、选项与批量判断。它们是借鉴方法，不是 DSH 命令授权认证。

建议先准备 150 条双人复核的授权样本：明确授权、无授权、撤回、引用命令、中文否定、路径越界、参数变体、注入与缺上下文，按项目/任务族分组留出测试集。使用原始概率、真实标签和 error/coverage、Brier、ECE、误放/误拦率；保留 none/unknown。高风险零误放不等于已证明足够安全：若独立试验中 n 条高风险样本零误放，95% 上界近似 3/n；150 条也只约 2%，且真实分布偏移会使该推断更弱。样本必须覆盖目标领域，不能仅凭“50–100 条”就承诺低风险。

### 可复用动作和本地模型：有价值，但先隔离实验

[JevDo](https://github.com/yinhong-zhou/jevdo) 的主要思路是重用已验证 Action，必要时才调用主模型。其新报告也说明冷启动学习成本与暖态复用收益必须分开，不能把几次重复任务的结果当作通用节省。我们更适合先做一个项目绑定、只读或固定验证命令的 recipe 实验，包含文件/配置指纹、工具可见性检查、原生权限和确定性后置条件；不自动学习并重放 Shell/发布/删除，不替换完整 Loop。

[Verdict](https://github.com/Manavarya09/verdict) 等本地兼容实现提供 `/v1/systemone` 和 abstain，可探索降低网络开销、离线和数据外发。但协议兼容不等于判断质量或校准兼容；当前 HTTP engine 还强制需要 key。需要独立 local 后端、仅 loopback 白名单、显式无鉴权选择与禁止转发云端 key，重新评估中文/越权样本。不能仅修改 endpoint 让用户携云端密钥访问任意本地/远程地址。

## 缓存约束：哪些改动允许，哪些要避免

[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/kv_cache/)仍要求完整匹配已持久化的前缀单元，命中为 best-effort。此次修复不动态改变提示词或工具列表，原生多轮回归检查旧历史前缀/目录一致。下一版的技能建议、监督结果继续追加，不剪 retained history、不每步裁剪工具、不每步切换主模型。

需要特别区分：JEV 自己输入变短/命中缓存，和主模型缓存不是同一个指标；少用一轮主模型可能让主模型缓存百分比降低但绝对耗费更少。报告应同时给 main hit/miss tokens、主模型请求数、JEV 请求/重试/耗时及总费用。上下文压缩只在宿主原本必须压缩的边界研究，不把每轮重写上下文当作优化。

## 建议的下一轮实验与验收门槛

先发布或验收 0.4.3 的可靠性修复。随后仅选择技能提示一个新能力，采用四组：标准、现有混合模式、代码候选提示、代码候选加 JEV 提示。后两组使用相同候选集，才能区分“代码提供线索”的收益和 JEV 的独立价值。先 30 个任务×3 次×4 组探索，再对有效任务族扩大样本；任务按运行顺序随机交错、相同工作区快照/主模型档位/工具权限，冷/暖会话分开。

预先登记：客观任务成功率、错误技能率、主模型请求/错误路径、总耗时中位数/P95及置信区间、main hit/miss、JEV 调用与重试、总费用。普通任务应保持零新增 JEV 调用；目标技能任务必须减少错误选择或主模型步骤，且无实质成功率损失。若总体 P95/费用上涨而收益不成立，不默认启用。对灰度授权另用隔离测试体和人工标签集评估，绝不拿真实删除/发布做实验。

这些是建议的实验门槛，不是已经实现的成绩。候选方案可被数据否决；“有意义”来自能消除已知故障、能独立归因、可回退，而不是功能数量。
