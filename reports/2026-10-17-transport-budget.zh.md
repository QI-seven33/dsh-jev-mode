## 最新资料给出的约束

- [TypeSafe Models](https://docs.typesafe.ai/models) 本轮仍列出 1.14.0，latest→1.13.0、preview→1.14.0。新模型可用不构成本项目迁移依据，继续固定 jev-1.13.0。官方同时提示中文等语言需按实际任务验证。
- [TypeSafe 重试说明](https://docs.typesafe.ai/sdk/python/api/retries) 明确总重试预算包含初次调用与等待，在等待将耗尽预算前停止；[JavaScript RetryPolicy](https://docs.typesafe.ai/sdk/javascript/api/interfaces/RetryPolicy) 包含抖动与服务端重试头。这里借鉴协议语义，保留零运行时依赖，没有叠加一层 SDK 重试。
- [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after) 允许 Retry-After 为秒数或 HTTP 日期。它给出的服务端等待不能被本地指数退避上限随意缩短。
- [DeepSeek 缓存说明](https://api-docs.deepseek.com/guides/kv_cache/) 仍要求完整匹配已持久化前缀单位，命中为 best effort。因此本次没有动态改系统提示、裁剪工具、重写旧历史或切换主模型。

## 为什么先选择这项改进

0.4.0 的历史 P95 恶化值得调查，但目前没有分解证据可以归因给某一个环节。先处理能复现的无效等待，收益边界比直接增加一个模型选择器更明确：服务端要求等 30 秒、当前决策只剩数百毫秒时，等待到超时不会产生一个有效重试。

0.4.3 的 backoffMs 会将服务端 30 秒压成 5 秒，并且不识别 HTTP 日期。只改这一函数仍不够：下一次独立决策会重新撞上同一限流。因此新增的核心思路是把服务端背压视为**后端实例的短期状态**，与“这个判断是否可信”和“这个动作是否获准”分开。

计划分为四步，已按此实施：复现不可完成的重试；修正期限/冷却和第二次凭据等待；以原生权限与旧版故障对照验证；只做三个合成真实请求确认连通性。没有把技能选择、模型迁移、阈值校准、分类器扩展或台账异步化混在一起。

## 实现与行为

1. 秒数、HTTP 日期及 retry-after-ms 均可进入重试安排；服务端等待不再压成 5 秒。仅本地指数退避添加 0–25% 随机减量，避免并发客户端整齐重试。若等待将达到或超出剩余决策期限，立即返回 unavailable。
2. 429/503 带明确等待时，当前 HTTP engine 实例记住冷却结束时间。当前调用可在预算内重试；后续调用在冷却中立即回退。它不存密钥、不存判断、不跨进程共享，不扩大可执行权限。
3. 未发请求的冷却跳过不增加熔断故障，不清空旧故障，也能释放半开探针。用户取消仍不算提供方故障。已在途请求不能追回；恢复后不会因其他请求成功就提前抹掉服务端冷却。
4. available 和 ask 分别解析凭据。第二次解析也遵守同一取消/期限；迟到结果被消费，不会发送请求。同步启动查询异常也被包含。每次操作仍重新解析凭据，轮换能力保留。
5. 内部管线和成功/降级台账添加五个数值：httpRequests、retries、retryWaitMs、cooldownSkips、retryBudgetSkips。真实 HTTP 尝试与决策次数分开，缓存命中记零新增请求。台账通过明确数值白名单过滤，没有保存任意 headers、正文或错误对象。公开工具 schema 保持不变。

本轮没有改造台账写入架构；慢磁盘仍可能延迟流程。冷却时更早回退可能增加普通规划或人工审批，不能宣称每个任务更快。没有服务端重试头的 429/503 仍使用原有有界重试和熔断，不虚构一个组织级限流器。

## 验证与测量

完整本机 npm test 通过，原有 12 项硬化加新增 14 项传输测试通过，含并发在途限流延长冷却的场景。真实宿主回归覆盖 V4 none/zstd、冷重开、旧历史前缀及工具目录不变；已授权隔离写入对照、等待/下游撤回及用户取消继续通过。额外的两种失败策略各尝试两次受保护写入：四个文件均未写入，每组仅一次 HTTP 请求。模拟服务端响应不能证明真实模型安全准确率。

另将三种 protocol 的实际注册内容与不可变 v0.4.3 入口逐项比较：静态提示、工具名称/描述、参数与输出 schema 全部一致。0.4.4 包在全新隔离 profile 通过原生 PluginManager 安装、自动启用、预设组合、全局设置和客户端发现；没有使用个人 profile 或凭据。这不是公开 GitHub/Release 安装验收，也不是桌面手工验收。

## 除已有方案之外，下一步还值得考虑什么

以下是新的设计推论，尚未实施，不能写成已经获得的收益：

1. **区分紧急授权与可放弃建议的排队资源。** 当前 FIFO 可让慢建议占满并发槽，使授权因排队而失败。可以为授权保留一个有界名额，过期建议先丢弃；不得抢占已执行的工具或降低授权标准。实验用两条慢建议夹一条授权，测最坏等待、取消公平性及总并发，先证明没有饥饿和请求放大。
2. **用决策的机会成本选择优化对象。** 同样减少一次主模型调用，若 JEV 本身比省下的步骤慢，就未必有益。把目标任务中的“可省步骤时间”和额外远端开销配对记录，冷/暖会话分开。先离线判断哪些任务族值得语义选择，之后只在建议通道试验局部开关；不自适应移动授权阈值，也不每轮改主模型前缀。
3. **记录执行结果与判断的差距。** 决策 allow、宿主准许、工具实际运行、后置条件成立是四件不同的事。未来用调用摘要连接这些事件，记录工具错误类别和确定性后置条件，同时保持元数据最小化。由此判断主要损失来自误选、权限等待还是执行失败，避免把“模型少调用一次”当作成功。
4. **对反复失败做有限的修复分流。** 可只把测试失败类别、错误指纹、已试方案的受限元数据交给已知 id/none 选择器，让主模型得到“补证据/运行已有检查/请求人工”提示。它不生成命令、不自动重放副作用；保留全部目录，只追加通知。先在人工标注的重复失败轨迹离线回放，确认减少重复错误后再做默认关闭的影子实验。这与技能目录推荐不同，目标是缩短错误循环。

优先级建议：先验收本候选的恢复行为；再做排队资源实验与执行结果归因。技能推荐仍值得保留，但只有独立测量证明它减少错误加载或主模型步骤，才推进 0.5.0。授权标注、命令覆盖、有界台账和宿主矩阵等原有欠账继续存在，不被这轮传输修复抵消。
