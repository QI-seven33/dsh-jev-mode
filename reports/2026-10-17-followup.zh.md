# 对第二轮评议的独立核对与后续探索

> 发布补记：本文保留审查时的候选状态。0.4.3 发布前已补齐取消/排队与后端故障隔离、凭据期限、授权快照及下游等待后的失效检查，并加入原生宿主回归。最终状态以 [CHANGELOG](../CHANGELOG.md) 和 [VALIDATION](../VALIDATION.md) 为准；新功能与模型实验仍未启用。

核对日期：2026-10-17。对象为本地 0.4.3 候选，公开版本仍为 0.4.2。本文没有发布版本、切换模型或运行计费 API 实验。

## 判断：发布路线合理，但有关键事实需要纠正

我同意先交付 UI 与可靠性修复，不在补丁版混入技能选择、调阈值、重写缓存或更换 Agent Loop。这也是上一份报告正文的顺序；此前结尾对技能提示的强调容易让人误读为“现在就加功能”，这里明确将它放回实验阶段。

不过，不能因为已有四项修复，就认为候选已穷尽发布前的可靠性问题。维护者收录是目录层面的认可，不是授权正确性、运行兼容性或性能认证。本轮继续用隔离脚本检查，发现两项需要补充验收的边界。

## 授权不是三选一：选项顺序实验应放到正确通道

当前 `CHANNELS.authorize` 使用 `primitive: noul`、`criteria: null`。JEV 回答“用户是否授权这项动作”的单一概率；代码随后将其映射为 allow/ask/deny，阈值为 0.85/0.55。三个结果不是交给模型选择的 options。

官方 [Noul](https://docs.typesafe.ai/primitives/noul) 和 [Choice](https://docs.typesafe.ai/primitives/choice) 明确区分这两种协议。前者是 yes 概率，后者才接收命名的候选项。官方文档还区分 question id 与 option name：question id 不展示给模型；Choice 的 option name 和 description 会展示。不能把两种“名字”混为一谈。

查到的 [finnhll/jev-eval 原始实验](https://github.com/finnhll/jev-eval) 确实报告一个歧义输入重排后概率从 0.62 变为 0.48；它同时说明选中类别没有变化，变化的是分布和置信度。不能将这个具体例子说成“已经切换了答案”，但其变化仍可能触发阈值分支。[更大规模的独立研究](https://github.com/gazelle93/decision-models-under-pressure) 则分别测量重排与同顺序重复，说明必须把顺序效应与调用噪声分开。

“blue 偏好”在汇总目录中有记录，但本次未成功读取对应原仓库及数据，因此不把它当作已独立复核的结论。无论这个例子是否成立，都不能直接证明当前 Noul 授权通道存在三选一标签偏好。官方 [Jev 1.13 已知局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13) 本身已承认 Choice 顺序、对抗内容、复杂否定和无关上下文等问题；它的适用范围是 1.13，不能不经验证就套到后续版本。

### 正确的校准控制项

授权 Noul：固定模型版本、原始状态和题目，重复测量；分别测试等义改写与中文否定、明确授权/撤回、同一动作换目标、一次许可/长期许可、正文引用与真实用户输入、历史截断与无关内容。真正改变授权语义的案例应改变人工标签，不能把“撤回前后不同结果”误记为不稳定。真实指令的时间顺序不能任意打乱后还假定真值相同。

Choice 选择器：固定候选集合、描述和 none 出口，仅置换顺序；另做同顺序重复控制。换标签名称、增删候选和改描述分别实验，不能混成一个变量。生产环境固定规范顺序；不为追求“排序不敏感”在每次调用中随机排序。

150 条案例只是起步，不足以许诺低危险误放率。150 个任务重复五次不是 750 个独立授权样本；近义变体也应按源任务分组，避免跨训练/验证泄漏。零误放的近似 3/n 上界适用于相应的独立危险测试案例，不能把全部混合任务数量都作分母。

## 补查到的重要新信息：Jev 1.14 已可用

上一份报告遗漏了这条模型更新，此处补正。官方 [Models](https://docs.typesafe.ai/models) 当前列出 `jev-1.14.0`，注明自 **2026-10-14** 可用；同时列明 `jev-latest` 仍指向 `jev-1.13.0`，`jev-preview` 指向 1.14。可用的新版本不等于 stable alias 已切换。

本插件 TypeSafe 默认已固定为 `jev-1.13.0`，不应误称它“默认在漂移”。可选 OpenRouter 配置用了另一服务的 latest 别名，其解析结果需要单独记录，不能直接套用 TypeSafe 的别名表。

真正值得优先做的模型实验：同一组已标注的 DSH 授权/中文/注入/歧义样本、固定题目，比较 1.13.0 与 1.14.0。保留原始输出、实际响应 model、schema 拒绝率、任务级错误、阈值翻转、延迟与总用量。先保留 0.85/0.55，观察新版本在相同规则下是否更好；不能只因“新版本”就复用旧校准或直接替换默认值。

官方页面未在此给出足以证明 DSH 授权更准或更快的对照数据，因此本报告不做这种承诺。当前输出解析没有将提供方实际 model 完整贯穿到台账，后续可增加不含正文的决策版本收据，记录请求/实际模型、题目修订、宿主版本与输入摘要。固定模型配置已经存在；收据补的是可追溯性。

## 继续检查后的两项新发现

脚本和结果位于工作区证据目录的 `followup-boundaries.mjs`、`followup-boundaries.json`。均使用脚本化提供方，未请求真实 JEV，未运行 Shell、发布或删除。

| 边界 | 当前候选的观察 | 应如何处理 |
| --- | --- | --- |
| 判断等待期间撤回授权 | 创建 gate 时有发布授权，JEV 等待期间加入撤回；脚本化返回 0.99 后，gate 仍给出 allow，提交给模型的旧 state 中没有撤回 | 增加原生宿主并发验收。若宿主不能保证取消，返回 allow 前核对授权修订、调用 id、参数摘要和取消状态；变化后丢弃旧结果并审批/重新判断 |
| 用户取消污染熔断 | 连续三次人为取消，被记成三次后端 failure；没有真实后端故障，后续决策仍进入 breaker | 将用户取消、排队期限耗尽、凭据故障与提供方可重试错误分开；取消不能把健康后端熔断，半开探针的释放仍需正确处理 |

第一项仅证明 createGate 层缺少快照失效检查，**不证明完整 Harness 里真实工具会在撤回后执行**；宿主可能提前中止回合或拒绝工具。第二项在同一个 pipeline 实例中复现，未据此声称所有窗口都共享熔断状态。还需将它们转成适用宿主的发布回归，再判断是否作为小型修复补入 0.4.3；不能将这两项记录成已经修复。

## 对“分类器与性能都不动”的补充判断

0.4.3 保持功能范围不扩大是合理的，已将已知漏检补入 VALIDATION.md。但“不是插件能单独完成”说得过满：支持明确语法的 `git -C`、`npm --prefix` 等，可以在插件中做有限参数解析并改善覆盖；未知脚本的真实副作用则不能仅凭命令名判断。继续研究结构化宿主信息是正确方向，但不是放弃所有插件侧改进的理由。

台账异步化可延后；不过磁盘等待没有上界会成为可用性问题，不能一概视作省几十毫秒的性能优化。更合适的边界是本次不重构写入架构，发布验收保留慢/失败存储与完整 deadline 检查，将有界异步队列排在独立后续修复。决策期限、凭据、排队和取消语义也属于可靠性，不属于可任意延期的缓存调参。

## 技能影子实验：不改变动作，不代表没有影响

影子模式仍会外发输入、消耗配额与费用；若在 pre-step 中 await，还会延迟真实主流程。默认应关闭，经明确启用后仅使用受限元数据，排入有界后台队列，超限或过期直接丢弃，不能写入模型上下文、阻止工具、改技能目录或触发重试风暴。

30 题×3 次影子采样可以发现推荐差异、错误样例和费用，但**不能证明启用后任务更快或更准**，因为推荐没有影响执行。先用人工标签评估候选/none 和稳定性，过关后再采用标准模式、当前混合模式、代码提示、代码加 JEV 提示的受控比较。四组比较能区分代码线索本身与 JEV 的独立增益。

## 更新后的优先顺序

1. 保持 0.4.3 的 UI 与原有四项可靠性修复；完成上述取消隔离和授权快照失效验收，公开已知分类器限制，整理可追溯的修复版。没有通过这些验收之前，不把“已有七项测试通过”当作全面发布结论。
2. 在固定协议和真实标注样本上做 1.13.0/1.14.0 对照，以及授权/Choice 各自适用的稳健性实验。不要直接升级默认模型或移动阈值。
3. 技能推荐保持独立实验分支、默认关闭、后台影子；先证明推荐有价值，再测其对真实任务的因果收益。
4. 后续再评估结构化命令覆盖、有界台账、受控 recipe 与本地决策模型，不把所有方向塞进同一次更新。

本轮只新增了文档与隔离探索证据，没有修改当前运行时、安装新实验功能、切换模型或发布 GitHub Release。可靠性修复应先交付，但“修复优先”必须允许发现新的发布阻断问题，而不应变成停止核查的理由。
